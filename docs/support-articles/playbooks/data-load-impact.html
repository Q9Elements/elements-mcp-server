Data Load Impact turns a planned Salesforce bulk data load into a ratified pre-load safety package, an optional small-batch sandbox rehearsal, and an ordered backlog for the customer's team. It analyzes the load and never performs the production load or changes Salesforce metadata.

What it does and when to use it

  • Use the playbook to understand what a planned load will fire, choose load parameters, identify safety controls, or plan a backfill rehearsal.
  • It predicts the transitive automation and locking effects of the specific load, audits bypass options, records the data-load owner's safety rulings, and prepares an ordered backlog.
  • The owner sees reasons to rehearse and chooses whether to use the recommended full-copy sandbox rehearsal. If rehearsal is skipped, the package states the risk.
  • The playbook analyzes only. The customer's team applies checklist changes and executes the production load and backlog.

Requirements

  • Install and connect the core elements plugin to the Elements Model Context Protocol (MCP) server. Core plan subscribers also need the Automation & Execution Intelligence add-on. See 'Connect your AI assistant to Elements' for core setup.
  • Access to the run_data_load_impact, list_reference_models, get_space_context, list_metadata_by_criteria, describe_metadata_schema, search_metadata, get_metadata_component, get_metadata_source, and explain_metadata_components tools.
  • Python 3 using the standard library only, and a host that runs the shipped local scripts, such as Claude Code or the Claude app.
  • The script host needs network access to Amazon Simple Storage Service (S3) for source downloads.
  • A named data-load owner, a planned source path or Salesforce Object Query Language (SOQL) file, and local access to the source files.
  • A full-copy sandbox when the owner chooses rehearsal. The Salesforce command-line interface (sf CLI) signed in to that sandbox is optional.
  • Privacy: on your computer in Claude Code or Codex command-line interface (CLI), the playbook reads load files, query results, and debug logs locally; the large language model (LLM) receives only counts, field names, and other summaries, never your record rows. In a chat app, an attached file is likely to be read into the LLM context, including its rows. To keep rows out of that context, attach a header-only file and give the approximate row count. For parent-heavy loads, we may also ask for a per-parent count and provide the query. Rehearsal files (loader success and error files, debug logs) belong in Claude Code or Codex CLI.

How it runs

  1. Kickoff: the owner provides their name and local source path. The playbook creates or resumes the engagement in the session working directory.
  2. Prerequisites: the playbook confirms the Elements connection, resolves the active Space and reference model, and checks required tools and source access.
  3. Intake manifest: the owner confirms the proposed object, operation, counted rows, written fields, loader, Application Programming Interface (API), and applicable upsert or portal-role facts in one reply. For update or upsert, the customer runs the generated SOQL query and saves its result locally.
  4. Impact analysis: the playbook analyzes the confirmed load and predicts its transitive automation and locking effects.
  5. Bypass audit: the playbook reviews downloaded metadata source files locally and records evidence for whether each predicted automation fires.
  6. Safety package ruling: the owner accepts or changes proposed actions and replacement checks, answers the incident-class question, and gives a go or no-go decision with any stated risks.
  7. Optional rehearsal: the owner chooses whether to rehearse in a full-copy sandbox. The playbook can slice up to 200 rows from a local comma-separated value (CSV) source. With a signed-in sf CLI that can match the ratified parameters, it runs the small test batch after the customer confirms the sandbox checklist is applied for that CLI user. Without the CLI path, the customer runs the batch manually and supplies same-job debug logs and loader success and error files.
  8. Backlog: after rehearsal is closed or skipped, the playbook delivers the ordered stories and final report.

What you get

  • report/final-report.md, the final safety and impact report.
  • Five or six ordered Markdown story files under stories/ for the customer's team to execute.

What stays with you

  • On your computer in Claude Code or Codex command-line interface (CLI), load files, query results, and debug logs stay local; the large language model (LLM) receives only counts, field names, and other summaries, never your record rows. In a chat app, an attached file is likely to be read into the LLM context, including its rows. To keep rows out of that context, attach a header-only file and give the approximate row count. Rehearsal files (loader success and error files, debug logs) belong in Claude Code or Codex CLI.
  • The customer applies checklist metadata changes, runs any manual rehearsal batch, and executes the production load and backlog.
  • The playbook never performs the production load or changes Salesforce metadata.
