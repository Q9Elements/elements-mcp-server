# Card script command lines

The examples run from the playbook repository. JSON means JavaScript Object Notation; API means application programming interface; MCP means Model Context Protocol; NDJSON means newline-delimited JSON; CSV means comma-separated values; HTTPS means Hypertext Transfer Protocol Secure; SHA-256 means Secure Hash Algorithm with a 256-bit digest. Every JSON input can hold inline values or paths to held files. Relative paths inside an input file resolve beside that input file; when absent there, a file beside the input folder is used. This accepts `work/drafts.json` from an input in `work/`. Every `--in` command writes JSON to `--out`, prints a one-line count and output path, and exits with a one-line error on invalid input.

```
python3 elements-change-impact/scripts/resolve_names.py --in input.json --out resolved.json
python3 elements-change-impact/scripts/build_change_set.py --in input.json --out change-set.json
python3 elements-change-impact/scripts/candidate_digest.py --in input.json --out candidates.json
python3 elements-change-impact/scripts/definitions_digest.py --in input.json --out definitions.json
python3 elements-change-impact/scripts/ooe_screen.py --in input.json --out ooe.json
python3 elements-change-impact/scripts/option_evidence.py --in input.json --out options-with-evidence.json
python3 elements-change-impact/scripts/existing_jobs.py shortlist --change-set change-set.json --objects Opportunity --dependents work/object-dependencies --out shortlist.json
python3 elements-change-impact/scripts/existing_jobs.py check --shortlist shortlist.json --summaries summaries.json --judgements judgements.json --dependents work/object-dependencies work/automation-dependencies --change-set change-set.json --out existing-jobs.json
python3 elements-change-impact/scripts/dependents_digest.py --in input.json --out dependents.json
python3 elements-change-impact/scripts/delete_order.py --in input.json --out delete-order.json
python3 elements-change-impact/scripts/fire_chain.py targets --in input.json --out fire-targets.json
python3 elements-change-impact/scripts/fire_chain.py digest --in input.json --out fire-digest.json
python3 elements-change-impact/scripts/plan_backlog.py --in input.json --out story-plan.json
python3 elements-change-impact/scripts/finish_backlog.py --in input.json --out backlog-result.json
python3 elements-change-impact/scripts/normalize_reads.py TOOL REPLY.json [REPLY.json ...] --work DIR [--parts-dir DIR]
python3 elements-change-impact/scripts/fetch_bundle.py --url URL --sha256 HEX --work DIR [--job-id HEX]
python3 elements-change-impact/scripts/render_report.py ENGAGEMENT_DIR
```

The cards reference scripts relative to their own steps directory. The command examples above use paths relative to the playbook repository.

`scripts/tests/__init__.py` makes test discovery importable with the plugin root as its top-level directory. Run `python3 elements-change-impact/scripts/lint.py` from the playbook repository to check the package.

`candidate` for schema evidence is the normalized `list_metadata_by_criteria` `rows.ndjson`. For automation evidence it is the incoming object dependency `dependents.csv`. `dependents` accepts several dependency bundles or files. The script reads each normalized folder's synthesized `manifest.json` inputs to distinguish a true zero from an element outside the read; supply `dependents_input_ids` for a bare file with zero rows. `target_facts` holds optional metadata node `nodes.ndjson` files or bundles. For named updates without an option round, pass only `targets` and held `target_facts` to `candidate_digest.py`. Field population is a percentage from held facts (`population.percent`); a schema candidate's `percent_filled` supplies it when node facts lack it. Missing population is "not known". `population.py` supplies the wording to the candidate digest, option evidence and report renderer. A failed dependents read passes its customer-word cause as `dependents_gap`; the output retains migration, population and pattern facts.

`existing_jobs.py` uses explicit file arguments, with paths relative to the working directory. Both commands print `<count> results: <out>` after writing JSON. Repeating `--dependents` or supplying several folders after it merges their normalized `dependents.csv` rows. `shortlist` accepts Flow, Process Builder, Process Builder Workflow, Apex Trigger, Apex Class and Workflow Rule candidates. Incoming rows supply candidate identity and active state; incoming read/write facts and outgoing read/write edges identify their objects. The target objects come from `--objects` plus the change set's elements, delta fields, `created_objects`, and held outgoing edges. Supply the object names resolved by card 01 through `--objects`, including when a decide request has `{"elements":[]}`. The flag accepts several names and can be repeated. A candidate must read or write a target object and is active unless a fact explicitly says otherwise. `active:false` or an inactive, draft, obsolete or deleted lifecycle status excludes it; null active with sync status `unchanged` remains eligible. Optional `--definitions` folders contain normalized `index.csv` files and their XML (Extensible Markup Language) definitions. An inactive or deleted definition excludes the candidate even when its active fact is null. Every automation the change creates, updates or deletes is excluded, including a named create without a node identifier. Package filtering uses `managedPackage` and `namespacePrefix` when supplied, plus a namespace prefix such as `pkg__` in the automation API name. The normalizer preserves these fields, `automation_status` and `operation`, plus `inputApiName`, `inputSfType` and `inputObject` for the source side of each dependency. Older normalized rows can use parent objects and the API-name prefix.

The shortlist output is:

```json
{"direction":"delete","deleted":[{"nodeId":"old","name":"Currency process","type":"Process Builder Workflow"}],"candidates":[{"nodeId":"helper","name":"CurrencyHelper","type":"Apex Class","objects":["Opportunity"]}],"summary_ids":["old","helper"]}
```

`direction` is `delete` for a delete-only change, `new` when nothing is deleted, and `both` otherwise. After shortlisting, read `get_dependencies` with `lookingFor:"using"` for the candidates and deleted automations in batches of at most 1,000. Save each reply with its `_call.nodeIds`, normalize it, and pass these folders with the held dependency folders to `check --dependents`. Then read summaries, write judgements and run `check`. Save `explain_metadata_components` replies for the returned `summary_ids`, using `aspect:"summary"` and at most 25 identifiers per call. `check --summaries` accepts several saved replies or repeated flags. Each reply is an `items` list of `{nodeId, aspect, status, narrative, confidence}` or a single such object. A saved `{_call, response}` envelope or a Model Context Protocol text-content envelope is accepted. Each item must have `status:"complete"`, `aspect:"summary"` and a nonempty narrative, and every requested summary must be present. Workflow Rules are judged from held definition text; omit `--summaries` when `summary_ids` is empty.

The runner writes this judgement shape, one item per job and candidate (or `candidate:null, verdict:"none"` when a job has no candidate):

```json
{"items":[{"direction":"delete","job":"Copy Opportunity currency to its Forecast Group","job_fields":["Opportunity_Forecast_Group__c.CurrencyIsoCode"],"creates_object":null,"candidate":"helper","verdict":"fit","reason":"The summary describes the currency copy."}]}
```

For `new`, the runner states `job_fields` and `creates_object` from the request in `judgements.json`; an empty change set is valid. For example, an empty set with `--objects Opportunity` and the request "create renewal opportunities" yields 1 scheduled Apex candidate; a judgement with `creates_object:"Opportunity"` and that candidate's outgoing object insert yields 1 fit. For `delete`, it splits each deleted automation's summary into jobs and takes their fields from that automation's outgoing writes. The write check keeps a `fit` or `partial` only when that candidate has an outgoing `write:true` Field edge to at least one `job_fields` entry, or an outgoing object write to `creates_object` whose structured `operation` is `insert` or `create`. When no structured operation is supplied, the normalizer accepts an exact operation-only relationship label such as `Insert` or `Create`. A description containing a record or action name, such as `Update Record 'Create renewal'`, supplies no creation operation. A read edge, an incoming edge, an object update, or a similarly worded summary cannot satisfy that check. A rejected verdict becomes `none` with `reason:"summary matches but it does not write <field>"`.

The result is `{"new":{"fits":[],"partials":[]},"delete":{"covered":[],"partly_covered":[],"lost":[],"ask":[]}}`. Entries retain the input job, candidate identifier and standing verdict, and add `name`, `type`, verbatim `summary`, `written_field`, `reason` and the original `model_reason`. A null candidate has null name, type, summary and written field; Workflow Rules have null summary. Delete entries group the same job, fields and creation object and retain every candidate's result in `assessments`. Any standing fit makes the job covered; otherwise a standing partial makes it partly covered with `lost_part:{job,reason}`; otherwise it is lost. `delete.ask` combines the lost and partly covered entries in job order; use a partial entry's `lost_part.job` and `lost_part.reason` for its uncovered work. A covered job contributes nothing to `ask`. The printed result count excludes this duplicate question list. For example, the C1 fixture has 3 candidates and 1 apparent purpose fit, but 0 currency-field writes: the result contains 1 lost job, and the handler's assessment records the downgrade.

Invalid input exits nonzero with one error line, for example `error: summary handler status: failed`, `error: candidate not in shortlist: handler`, or `error: delete job has no item`. Every deleted Field write must appear in a delete judgement's `job_fields`; an omitted write also fails. The runner owns complete semantic job decomposition, including jobs that have no Field writes. Card 02 asks one question for every `delete.ask` entry, persists `delete-loss-open` while awaiting the answer, and resumes from saved evidence. A delete-only change with an empty `ask` or `delete_anyway` goes directly to card 03 using card 01's asserted change set. A `move` answer puts every uncovered job into the normal option pick, with the replacement ordered before deletion.

`existing_automation` has `fits`, `partials`, `covered`, `partly_covered`, `lost` and `delete_answer`. The answer is null or `{"choice":"delete_anyway"|"move","verbatim":"<runner reply>"}`. A fit leads the report with "You already have this" and its candidate's name, type, verbatim summary and written field. Covered jobs say "Covered by <name>, which writes <field>." Summaries and written fields are TOOL EVIDENCE; verdicts and reasons are ANALYST JUDGEMENT. An empty existing-automation section renders nothing.

`normalize_reads.py` accepts the five tool names in its table row. Save either a plain tool reply or `{"_call": {"nodeIds": [...]}, "response": <reply>}`. Retaining the original arguments makes successful zero-row dependency reads distinguishable from unread inputs; with plain replies, only supplied or observed input identifiers can be recorded. Single-node calls use `_call.nodeId`. Component replies may be inline full documents, `items` replies or a verified `delivery:"file"` JSON pointer. A single component document's `status` is preserved as metadata. Job envelope statuses are checked on replies for all five tools; a running or failed job publishes no normalized output. Metadata statuses inside documents, items and verified parts retain their source values. Their output folder name is a digest of the saved replies when the tool supplies no `resultId`.

The converter downloads HTTPS parts, verifies SHA-256, byte size, per-part row count and merged `totalRows`, then publishes `work/<resultId>/`. Parts merge in numeric index order; each CSV part's repeated header is consumed once. Supply further reply files for every `nextPartsFrom` continuation. A changed `resultId` discards held parts and returns a one-line error asking for a restart with one result. `--parts-dir` reads already-downloaded files by their URL basename or `part-<index>.<format>` for offline use, with the same integrity checks. A missing continuation, expired link, integrity mismatch or tool refusal exits nonzero without publishing a normalized folder. Errors report the tool code even when its message is absent.

For example, a dependency read requests A and B and returns three rows. B fails with `deadline_exceeded` and `rowsWritten: 1`. The converter verifies all three rows, drops B's one row, writes A's two rows, and records `inputs.nodeIds: ["A"]`, `totals.rows: 2` and B's failure in the manifest. Re-read B independently and pass both successful folders to the existing scripts. Full component facts map `impactDetails.impactByFilled.percent` to `population.percent`. A dependency's null `lastRun` becomes an empty `lastUsed`. Source rows retain unavailable reasons and object-scoped definitions; `definitions_digest.py` can digest whole-object XML larger than 1.97 MB.

`fetch_bundle.py` downloads complete `run_data_load_impact` zips into `work/<jobId>/`. The identifier must be hexadecimal. `--job-id` selects it; `--result-id` is accepted as a command-line alias, and an omitted identifier uses the supplied digest. The command prints the extracted folder and `manifest.json` path when present, or `coverage.json` otherwise. Its Python `refetch()` callback takes no arguments and repeats the original tool call captured by the caller. The runner refreshes an expired pointer or a failed integrity check by repeating `run_data_load_impact` with identical original arguments, then invokes the command again. `render_report.py` writes `impact-report.html` beside `impact-report.json` in the engagement directory. A fixed mapping inside the renderer labels every section or item as TOOL EVIDENCE or ANALYST JUDGEMENT (decision D58 (3)). Tool reads and script outputs, including counts, computed dispositions, fire-chain rows, dependents, populations and lock rows, are TOOL EVIDENCE. Corrections, option rationale, option summaries, judgement dispositions and backlog prose are ANALYST JUDGEMENT. Order rows keep the script-produced `reason` as TOOL EVIDENCE. Put entry-condition comparisons and downgrade reasons in a separate `analyst_note`, leaving `reason` intact. The note and the shown row status are ANALYST JUDGEMENT when the note is non-null; the option order summary also carries that label when any peer has a note. Rows without a note render their status and reason as TOOL EVIDENCE. The renderer uses this explicit field rather than parsing reason text. Dependent rows with `analyst_note` likewise retain script reasons and report text as TOOL EVIDENCE while labelling the shown disposition and note ANALYST JUDGEMENT. A trigger-field check copied from the held fire-chain digest is TOOL EVIDENCE; report-authored trigger-field comparisons are ANALYST JUDGEMENT. Evidence drawer facts and lines are TOOL EVIDENCE; findings and model text are ANALYST JUDGEMENT. Mixed sections override the section label on individual items. The runner supplies the existing report fields.

`render_report.py` reads referenced fire-chain, order-of-execution, delete-order and dispositions JSON files from the engagement directory and embeds their contents in the page. Each order-of-execution block uses its option label for an option round, its saved element label for an update, or plain "Order of execution". The space is its name, whether supplied as a string or an `{id,name,how}` object; pre-existing conflicts are identified without inviting another pick. Dependent counts use `impacted_components.members` or, when empty, the dispositions file's `units`. A mixed change set names each element's incoming and outgoing counts and groups outgoing connections separately from impacted dependents. `impacted_components.read_counts` maps a changed node identifier to the assessed directions, for example `{"flow":{"outgoing":45},"rule":{"incoming":0}}`. Card 04 fills these counts from successful held reads, including empty reads; an omitted direction is "not assessed". Member rows with `direction` and `inputNodeId` also prove a nonzero read. For example, 45 outgoing Flow connections and 0 incoming rule references give those two counts, with the Flow's incoming references and the rule's outgoing connections marked "not assessed". A missing referenced file appears as `not available (file missing)`. Set `review_before_build.fire_chain_unavailable` to a customer-word cause, or `model_not_synced` for a model sync in progress; the report gives it its own save-driven-effects line. The report shows partial coverage once, lists every next-hop object found in the fire digest, counts judged updates within the update total, names recent reports, and counts older or undated reports with work by member row in the members file. When `zero_dependents` is true, an automation update with only outgoing connections says incoming references were not read; an update or delete with an incoming read may say nothing references the target once per element. Option evidence gives dependent totals by type and population for existing fields. Evidence drawers use customer sentences and omit raw definition fragments and internal source paths. Blocking findings appear under "Findings to resolve before build"; other findings appear under "Findings". Model sync times use Coordinated Universal Time (UTC). A sync date without a time says that the UTC time was not recorded. `change_request.model.last_sync` holds `syncRecency.metadataGraphSyncedAt`; a non-null timestamp permits analysis even when `metadataSyncStatus` is `"failed"`. Card 01 sets `change_request.model.latest_sync_failed` to that status comparison, and card 04 copies it into the report. A true value renders "The latest sync failed; this analysis uses the last complete sync." Only a null graph timestamp is `model_not_synced`.

`plan_backlog.py` leaves delta details for the card to express in customer words. Its fixed criteria cover migration, deploy order and applicable delete checks. A blocking finding enters the story for its `element`; text matching supplies the element when that field is absent. Slash and backslash spellings match. `delta.length` holds the new field length; a reduction gets a criterion to export and resolve longer existing values before shortening. Writer fixes precede a late field change and may deploy earlier than a length reduction; record-type value availability and report verification follow that change; all updates precede deletes. A dependent that references a field type change gets a criterion naming the change story's step and requiring the same deployment. Record-type values deploy with or after the type change. A restricted picklist gets a migration criterion for existing unlisted values. A Field delete has no deactivation criterion. A delete checks replacement flows when its `replacement` matches a Flow create or update by node id, label or API name. Migration causes share one sentence so the card can write 3 to 6 criteria per story. Substantive answers with `kind: "requirement"` enter the plan, including replies to plan the confirmed change anyway; card 04 places them verbatim on the matching change story. A bare confirmation contributes no requirement. Pass each explicit story request as a `requested_stories` item with `summary` and verbatim `request`; the plan places these requested entries before change stories. Older or undated report dependents of the same relation and disposition share one story with all members; recent reports stay named individually, including when the input supplies grouped units. The finisher requires one draft per entry, preserves `Request, verbatim:` with that entry's request on requested stories, marks their Markdown headings `[requested]` and rejects extra drafts. Named delete-order rows are accepted for story sequencing. `finish_backlog.py` uses the plan summary when an inactive delete draft puts "Deactivate" in its summary.

For `finish_backlog.py`, set `requirement` to `change_request.sentence`. The finisher fills `Request, verbatim:` on change stories and removes that marker from dependent stories. `Answer, verbatim:` lines retain their text. A missing `problem_statement` comes from the first description line and appears once in the Markdown backlog. The finisher checks requirement answers against all story text, including line breaks. A plan entry's nonempty flag note takes precedence; otherwise the draft story's flag note is kept. The plan's `member_groups` are written alongside story member files; older reports with work go in `members/older-reports.csv`. Backlog story links appear only for that story's members. A members file includes the `elements_link` column when every member has a link.

`delta_keys.py` is the shared delta vocabulary for the dependent digest and backlog plan. Value additions use `values_added`. Value removals use `values_removed`, `values_deleted`, `value_deleted`, or `deleted_values`. Deactivations use `values_deactivated`, `value_deactivated`, or `deactivated`. Renames use `values_renamed`, `api_names_renamed`, `label`, `new_label`, `label_rename`, `api_name`, `new_api_name`, or `api_name_rename`. Report and list-view filter stories use removals, deactivations, and renames. Record-type value stories use additions and removals. The migration rule uses `type`, `data_type`, `length`, `values_removed`, `field_required`, and `restricted`. A named automation update records a changed proposed entry condition as `entry_condition_change` in its delta for order-of-execution screening.

`finish_backlog.py` writes a held or incomplete backlog with `drafted: false`, `status: "not drafted"`, its full `reason` and an empty story list. Put "not drafted: resolve the blocking finding first" and the finding text in `incomplete.reason` to use this path for a held backlog. Card 04 skips the plan when a blocking finding exists and `change_request.plan_despite_findings` is not true, and delivers the full report with these files. Card 01 sets that flag true for a reply to plan the confirmed change anyway and records it as a requirement answer; a new request or correction writes the flag false.
