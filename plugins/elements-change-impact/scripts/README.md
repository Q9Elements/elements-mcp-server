# Card script command lines

The examples run from the playbook repository. JSON means JavaScript Object Notation; API means application programming interface; MCP means Model Context Protocol; NDJSON means newline-delimited JSON; CSV means comma-separated values; HTTPS means Hypertext Transfer Protocol Secure; SHA-256 means Secure Hash Algorithm with a 256-bit digest. Every JSON input can hold inline values or paths to held files. Relative paths inside an input file resolve beside that input file; when absent there, a file beside the input folder is used. This accepts `work/drafts.json` from an input in `work/`. The `engagement` path supplied to `plan_backlog.py` is relative to the process working directory; an absolute path is accepted. Every `--in` command writes JSON to `--out`, prints a one-line count and output path, and exits with a one-line error on invalid input.

```
python3 elements-change-impact/scripts/resolve_names.py --in input.json --out resolved.json
python3 elements-change-impact/scripts/build_change_set.py --in input.json --out change-set.json
python3 elements-change-impact/scripts/candidate_digest.py --in input.json --out candidates.json
python3 elements-change-impact/scripts/definitions_digest.py --in input.json --out definitions.json
python3 elements-change-impact/scripts/ooe_screen.py --in input.json --out ooe.json
python3 elements-change-impact/scripts/option_evidence.py --in input.json --out options-with-evidence.json
python3 elements-change-impact/scripts/existing_jobs.py shortlist --change-set change-set.json --objects Opportunity --dependents work/object-dependencies --out shortlist.json
python3 elements-change-impact/scripts/existing_jobs.py check --shortlist shortlist.json --summaries summaries.json --judgements judgements.json --dependents work/object-dependencies work/automation-dependencies --change-set change-set.json --out existing-jobs.json
python3 elements-change-impact/scripts/dependents_digest.py --in input.json --out dependents.json
python3 elements-change-impact/scripts/delete_order.py --in input.json --out delete-order.json
python3 elements-change-impact/scripts/fire_chain.py targets --in input.json --out fire-targets.json
python3 elements-change-impact/scripts/fire_chain.py digest --in input.json --out fire-digest.json
python3 elements-change-impact/scripts/plan_backlog.py --in input.json --out story-plan.json
python3 elements-change-impact/scripts/finish_backlog.py --in input.json --out backlog-result.json
python3 elements-change-impact/scripts/normalize_reads.py TOOL REPLY.json [REPLY.json ...] --work DIR [--parts-dir DIR]
python3 elements-change-impact/scripts/fetch_bundle.py --url URL --sha256 HEX --work DIR [--job-id HEX]
python3 elements-change-impact/scripts/render_report.py ENGAGEMENT_DIR
```

The cards reference scripts relative to their own steps directory. The command examples above use paths relative to the playbook repository.

`cli_common.py` owns `normalize_type`, which maps type aliases to synced Salesforce type names before script comparisons. For example, Process Builder and ProcessBuilder become Process Builder Workflow, ApexTrigger becomes Apex Trigger, ApexClass becomes Apex Class, ValidationRule becomes Validation Rule, WorkflowRule becomes Workflow Rule, and CustomField becomes Field. Hard-coded type sets use synced names. Its shared `field_object` helper reads `object`, `parentObject`, `parent_object`, identity paths and dotted API names; field consumers use that helper.


`scripts/tests/__init__.py` makes test discovery importable with the plugin root as its top-level directory. Run `python3 elements-change-impact/scripts/lint.py` from the playbook repository to check the package, including identical required tool lists in the README and skill entrypoint.

`dependents_digest.py` runs once per changed element with that element's `input_node_id` and mode. For example, a page placement update and a Flow write update share one dependency bundle: the page call uses `placement_update`, and the Flow call uses `value_update`. Merge each call's units once. Pass the full change set to each call so a field value addition can find its automation writer.

`candidate` for schema evidence is the normalized `list_metadata_by_criteria` `rows.ndjson`. For automation evidence it is the incoming object dependency `dependents.csv`. `dependents` accepts several dependency bundles or files. The script reads each normalized folder's synthesized `manifest.json` inputs to distinguish a true zero from an element outside the read; supply `dependents_input_ids` for a bare file with zero rows. `target_facts` holds optional metadata node `nodes.ndjson` files or bundles. For named updates without an option round, pass only `targets` and held `target_facts` to `candidate_digest.py`. Field population is a percentage from held facts (`population.percent`); a schema candidate's `percent_filled` supplies it when node facts lack it. Optional held `fields` supply population by node identifier when both target facts and candidates lack it, including in automation runs. Zero is a known population. Missing population is "not known". `population.py` supplies the wording to the candidate digest, option evidence and report renderer. A failed dependents read passes its customer-word cause as `dependents_gap`; the output retains migration, population and pattern facts.

`existing_jobs.py` uses explicit file arguments, with paths relative to the working directory. Both commands print `<count> results: <out>` after writing JSON. Repeating `--dependents` or supplying several folders after it merges their normalized `dependents.csv` rows. `shortlist` accepts Flow, Process Builder, Process Builder Workflow, Apex Trigger, Apex Class and Workflow Rule candidates. Incoming rows supply candidate identity and active state; incoming read/write facts and outgoing read/write edges identify their objects. The target objects come from `--objects` plus the change set's elements, delta fields, `created_objects`, and held outgoing edges. Supply the object names resolved by card 01 through `--objects`, including when a decide request has `{"elements":[]}`. The flag accepts several names and can be repeated. A candidate must read or write a target object and is active unless a fact explicitly says otherwise. `active:false` or an inactive, draft, obsolete or deleted lifecycle status excludes it; null active with sync status `unchanged` remains eligible. Optional `--definitions` folders contain normalized `index.csv` files and their XML (Extensible Markup Language) definitions. An inactive or deleted definition excludes the candidate even when its active fact is null. Every automation the change creates, updates or deletes is excluded, including a named create without a node identifier. Package filtering uses `managedPackage` and `namespacePrefix` when supplied, plus a namespace prefix such as `pkg__` in the automation API name. The normalizer preserves these fields, `automation_status` and `operation`, plus `inputApiName`, `inputSfType` and `inputObject` for the source side of each dependency. Older normalized rows can use parent objects and the API-name prefix.

The shortlist output is:

```json
{"direction":"delete","deleted":[{"nodeId":"old","name":"Currency process","type":"Process Builder Workflow"}],"candidates":[{"nodeId":"helper","name":"CurrencyHelper","type":"Apex Class","objects":["Opportunity"]}],"summary_ids":["old","helper"]}
```

`direction` is `delete` for a delete-only change, `new` when nothing is deleted, and `both` otherwise. After shortlisting, read `get_dependencies` with `lookingFor:"using"` for the candidates and deleted automations in batches of at most 1,000. Save each reply with its `_call.nodeIds`, normalize it, and pass these folders with the held dependency folders to `check --dependents`. Then read summaries, write judgements and run `check`. Save `explain_metadata_components` replies for the returned `summary_ids`, using `aspect:"summary"` and at most 25 identifiers per call. `check --summaries` accepts several saved replies or repeated flags. Each reply is an `items` list of `{nodeId, aspect, status, narrative, confidence}` or a single such object. A saved `{_call, response}` envelope or a Model Context Protocol text-content envelope is accepted, including text wrapped in `[TOOL DATA START]` and `[TOOL DATA END]`. Both summary and normalization readers use the shared `tool_reply.py` unwrap; marker-free replies pass through unchanged. Narrative accepts a string or `{purpose, text}`; nonblank `text` is kept verbatim, falling back to `purpose`. Each item must have `status:"complete"`, `aspect:"summary"` and a nonempty narrative, and every requested summary must be present. Workflow Rules are judged from held definition text; omit `--summaries` when `summary_ids` is empty.

The runner writes this judgement shape, one item per job and candidate (or `candidate:null, verdict:"none"` when a job has no candidate):

```json
{"items":[{"direction":"delete","job":"Copy Opportunity currency to its Forecast Group","job_fields":["Opportunity_Forecast_Group__c.CurrencyIsoCode"],"creates_object":null,"candidate":"helper","verdict":"fit","reason":"The summary describes the currency copy."}]}
```

For `new`, the runner states `job_fields` and `creates_object` from the request in `judgements.json`; an empty change set is valid. For example, an empty set with `--objects Opportunity` and the request "create renewal opportunities" yields 1 scheduled Apex candidate; a judgement with `creates_object:"Opportunity"` and that candidate's outgoing object insert yields 1 fit. For `delete`, it splits each deleted automation's summary into jobs and takes their fields from that automation's outgoing writes. The write check keeps a `fit` or `partial` only when that candidate has an outgoing `write:true` Field edge to at least one `job_fields` entry, or an outgoing object write to `creates_object` whose structured `operation` is `insert` or `create`. When no structured operation is supplied, the normalizer accepts an exact operation-only relationship label such as `Insert` or `Create`. A description containing a record or action name, such as `Update Record 'Create renewal'`, supplies no creation operation. A read edge, an incoming edge, an object update, or a similarly worded summary cannot satisfy that check. A rejected verdict becomes `none` with `reason:"summary matches but it does not write <field>"`.

The result is `{"new":{"fits":[],"partials":[]},"delete":{"covered":[],"partly_covered":[],"lost":[],"ask":[]}}`. Entries retain the input job, candidate identifier and standing verdict, and add `name`, `type`, verbatim `summary`, `written_field`, `reason` and the original `model_reason`. A null candidate has null name, type, summary and written field; Workflow Rules have null summary. Delete entries group the same job, fields and creation object and retain every candidate's result in `assessments`. Any standing fit makes the job covered; otherwise a standing partial makes it partly covered with `lost_part:{job,reason}`; otherwise it is lost. `delete.ask` combines the lost and partly covered entries in job order; use a partial entry's `lost_part.job` and `lost_part.reason` for its uncovered work. A covered job contributes nothing to `ask`. The printed result count excludes this duplicate question list. For example, the C1 fixture has 3 candidates and 1 apparent purpose fit, but 0 currency-field writes: the result contains 1 lost job, and the handler's assessment records the downgrade.

Invalid input exits nonzero with one error line, for example `error: summary handler status: failed`, `error: candidate not in shortlist: handler`, or `error: delete job has no item`. Every deleted Field write must appear in a delete judgement's `job_fields`; an omitted write also fails. The runner owns complete semantic job decomposition, including jobs that have no Field writes. Card 02 asks one question for every `delete.ask` entry, persists `delete-loss-open` while awaiting the answer, and resumes from saved evidence. A delete-only change with an empty `ask` or `delete_anyway` goes directly to card 03 using card 01's asserted change set. A `move` answer puts every uncovered job into the normal option pick, with the replacement ordered before deletion.

`resolve_names.py` reads `hits` as inline rows, a JSON list file, an NDJSON row file or a downloaded `search_metadata` object with `nodes`. For example, `{"targets":[{"name":"Type","sfType":"Field","object":"Opportunity"}],"hits":"work/search.json"}` reads `{"nodes":[<metadata rows>],...}`. A saved response envelope also resolves locally. A list of file paths combines typed groups and pages, deduplicating node identifiers. Card 01 makes one initial search per implied type with `sfType` set, `limit:200` and `delivery:"file"`; unknown types share one untyped call. It pages with `skip` while `hasMore` only until every form has an exact-name hit or the results end, then passes the downloaded paths as `hits`.

`normalize_reads.py` accepts the five tool names in its table row. Save a plain tool reply, `{"_call": {"nodeIds": [...]}, "response": <reply>}`, or a minimal manifest `{"_call":{<original arguments>},"resultId":"<resultId>","totalRows":<count>,"parts":[{"index":0,"url":"<url>","format":"ndjson","sha256":"<digest>","rows":<count>,"expiresInSeconds":<seconds>}]}`. Each part retains its original index and format. Keep `failed`, `failedTotal`, `failedFile`, `partsTotal` and `nextPartsFrom` when supplied; `partsTotal` can be inferred from a complete list. Byte sizes are optional and are verified when present. The manifest and verbatim reply produce identical normalized files. An empty `parts` list with `totalRows:0` records a completed empty read. Retaining the original arguments makes successful zero-row dependency reads distinguishable from unread inputs; with plain replies, only supplied or observed input identifiers can be recorded. Single-node calls use `_call.nodeId`. Component replies may be inline full documents, `items` replies or a verified `delivery:"file"` JSON pointer. A complete file delivery with `_truncated.inFile:true` and `hasMore:false` is accepted; checksums, bytes and file row counts still apply. A reply with more pages or truncated inline content fails without publishing a folder. A single component document's `status` is preserved as metadata. Job envelope statuses are checked on replies for all five tools; a running or failed job publishes no normalized output. Metadata statuses inside documents, items and verified parts retain their source values. Their output folder name is a digest of the saved replies when the tool supplies no `resultId`.

The converter downloads HTTPS parts, verifies SHA-256, byte size, per-part row count and merged `totalRows`, then publishes `work/<resultId>/`. Parts merge in numeric index order; each CSV part's repeated header is consumed once. Supply further reply files for every `nextPartsFrom` continuation. A changed `resultId` discards held parts and returns a one-line error asking for a restart with one result. `--parts-dir` reads already-downloaded files by their URL basename or `part-<index>.<format>` for offline use, with the same integrity checks. A missing continuation, expired link, integrity mismatch or tool refusal exits nonzero without publishing a normalized folder. Errors report the tool code even when its message is absent.

For example, a dependency read requests A and B and returns three rows. B fails with `deadline_exceeded` and `rowsWritten: 1`. The converter verifies all three rows, drops B's one row, writes A's two rows, and records `inputs.nodeIds: ["A"]`, `totals.rows: 2` and B's failure in the manifest. Re-read B independently and pass both successful folders to the existing scripts. Full component facts map `impactDetails.impactByFilled.percent` to `population.percent`. A dependency's null `lastRun` becomes an empty `lastUsed`. Source rows retain unavailable reasons and object-scoped definitions; `definitions_digest.py` can digest whole-object XML larger than 1.97 MB.

`fetch_bundle.py` downloads complete `run_data_load_impact` zips into `work/<jobId>/`. The identifier must be hexadecimal. `--job-id` selects it; `--result-id` is accepted as a command-line alias, and an omitted identifier uses the supplied digest. The command prints the extracted folder and `manifest.json` path when present, or `coverage.json` otherwise. Its Python `refetch()` callback takes no arguments and repeats the original tool call captured by the caller. The runner refreshes an expired pointer or a failed integrity check by repeating `run_data_load_impact` with identical original arguments, then invokes the command again. `render_report.py` writes `impact-report.html` beside `impact-report.json` in the engagement directory. A fixed mapping inside the renderer labels every section or item as TOOL EVIDENCE or ANALYST JUDGEMENT (decision D58 (3)). Tool reads and script outputs, including counts, computed dispositions, fire-chain rows, dependents, populations and lock rows, are TOOL EVIDENCE. Corrections, option rationale, option summaries, judgement dispositions and backlog prose are ANALYST JUDGEMENT. Order rows keep the script-produced `reason` as TOOL EVIDENCE. Put entry-condition comparisons and downgrade reasons in a separate `analyst_note`, leaving `reason` intact. The note and the shown row status are ANALYST JUDGEMENT when the note is non-null; the option order summary also carries that label when any peer has a note. Rows without a note render their status and reason as TOOL EVIDENCE. The renderer uses this explicit field rather than parsing reason text. Dependent rows with `analyst_note` likewise retain script reasons and report text as TOOL EVIDENCE while labelling the shown disposition and note ANALYST JUDGEMENT. A trigger-field check copied from the held fire-chain digest is TOOL EVIDENCE; report-authored trigger-field comparisons are ANALYST JUDGEMENT. Evidence drawer facts and lines are TOOL EVIDENCE; findings and model text are ANALYST JUDGEMENT. Mixed sections override the section label on individual items. The runner supplies the existing report fields.

`render_report.py` reads referenced fire-chain, order-of-execution, delete-order and dispositions JSON files from the engagement directory and embeds their contents in the page. Each order-of-execution block uses its option label for an option round, its saved element label for an update, or plain "Order of execution". The space is its name, whether supplied as a string or an `{id,name,how}` object; pre-existing conflicts are identified without inviting another pick. Dependent counts use `impacted_components.members` or, when empty, the dispositions file's `units`. A mixed change set names each element's incoming and outgoing counts and groups outgoing connections separately from impacted dependents. `impacted_components.read_counts` maps a changed node identifier to the assessed directions, for example `{"flow":{"outgoing":45},"rule":{"incoming":0}}`. Card 04 fills these counts from successful held reads, including empty reads; an omitted direction is "not assessed". Member rows with `direction` and `inputNodeId` also prove a nonzero read. For example, 45 outgoing Flow connections and 0 incoming rule references give those two counts, with the Flow's incoming references and the rule's outgoing connections marked "not assessed". A missing referenced file appears as `not available (file missing)`. Set `review_before_build.fire_chain_unavailable` to a customer-word cause, or `model_not_synced` for a model sync in progress; the report gives it its own save-driven-effects line. The report shows partial coverage once, lists every next-hop object found in the fire digest, counts judged updates within the update total, names recent reports, and counts older or undated reports with work by member row. Their full-list link uses the grouped review story's written members file and matches real API names, including when that file also lists recent reports or dashboards. A supplied `older_reports_file` or legacy older-report group remains a fallback when it exactly lists the older reports with work. When `zero_dependents` is true, an automation update with only outgoing connections says incoming references were not read; an update or delete with an incoming read may say nothing references the target once per element. Option evidence gives dependent totals by type and population for existing fields. Evidence drawers use customer sentences and omit raw definition fragments and internal source paths. Blocking findings, including top-level backlog flags, lead the report under "Findings to resolve before build", ahead of existing fits; other findings appear under "Findings". Model sync times use Coordinated Universal Time (UTC). A sync date without a time says that the UTC time was not recorded. `change_request.model.last_sync` holds `syncRecency.metadataGraphSyncedAt`; a non-null timestamp permits analysis even when `metadataSyncStatus` is `"failed"`. Card 01 sets `change_request.model.latest_sync_failed` to that status comparison, and card 04 copies it into the report. A true value renders "The latest sync failed; this analysis uses the last complete sync." Both templates also carry `latest_sync_in_progress`; a true value renders "A newer sync is in progress; this analysis uses the last complete sync." beside the analysed graph date. Only a null graph timestamp is `model_not_synced`. The report template leaves `impacted_components.older_reports_file` null until an actual member file is supplied.

A finding is blocking only when no backlog story resolves it and it makes the change unsafe as planned. Findings resolved by backlog stories stay in the report with `blocking:false`.

`plan_backlog.py` creates one change story for each non-keep change-set element. An all-keep set retains one adoption change story. Explicit `requested_stories` become change entries marked `requested:true`, carrying the verbatim `request`; the finisher marks their Markdown headings `[requested]` and requires that request in the prose. All entries belong to one of four kinds: `change`, `defect`, grouped `review` and `regression`. Normal plan order follows those kinds. Deployment dependencies take precedence: dependent fixes precede restrictions and migration changes, and an automation create or update that writes a field with `values_added` follows the dependent defect and grouped review work, before regression. Updates precede deletes within the change and defect work; `delete_order` orders consumers before their deleted targets. Regression is last.

A card-judged UPDATE, DELETE or DELETE_CANDIDATE dependent has one defect story across all changed elements and direct or formula paths. Its `input_ids` identify every changed source, and `sources` retains each input unit with its relations and judgement, including nested relation evidence. Script-decided dependents share review stories: Reports and Dashboards together, List Views separately, every other type by type and relation. A grouped digest input and individual units produce the same members. Every work member appears in `members/<story-id>.csv`, recent members first, with newer usage first within each recency group. Member rows keep `name` (display label), `api_name` (real API name, empty when unavailable), `type` and `last_used`. `elements_link` appears when every member has a link. Member files contain these columns, and Markdown stories use display names as targets. The story plan and backlog record retain source identifiers and relation evidence for coverage checking. The finisher checks every disposition against plan targets and members before writing files.

Filter review for an added value has three fixed criteria: each owner records whether its component counts the new value, included filters contain that value, and each total reconciles to a direct count of the records that its filter includes. A component excluding the new value is lower by that value's record count. Other reviews require each member's use to be checked and updated or marked no change. UNKNOWN and REVIEW work remains grouped with an impact-not-confirmed flag.

Change criteria cover migration, deploy order and applicable delete checks. A created required Field requires blank existing values to be backfilled before enforcing its requirement. `delta.length` carries the new length, with an export and resolution criterion before shortening. Field type changes and their dependent fixes share a deployment; Record Type available values follow that change. A grouped Record Type review combines deployment requirements for multiple fields into one criterion naming each field and its step, keeping its fixed criteria within the six-criterion cap. A restricted picklist requires mapping existing unlisted values. A Field or inactive automation delete has no deactivation criterion. Replacement checks apply when `replacement` names a Flow create or update by identifier, label or API name. Boundary cases of the change's own condition belong in that change story's acceptance criteria.

The optional `regression` input is a list of card-supplied cross-story interactions. Each item has `kind` (`duplicate_creators`, `shared_parent_lock` or `shared_write`) and a nonempty `outcome`, worded as an end-to-end result. Card 03 saves `{kind,outcome,elements}` items in `analysis.regression` in the execution state and replaces the list on each trace, including an empty list when none apply. The state template documents each item in `_regression_shape`. Card 04 passes that saved list to the planner; a TR-05 redelivery reuses it when card 03 is skipped. An optional `elements` list names the changed elements the interaction rests on, so its regression story inherits their assumptions. Identifiers, labels and API names resolve in both directions against the held change set. Empty or omitted input gives no regression story. A nonempty list gives exactly one final story, with exactly one fixed criterion per interaction and no extra criteria. For example:

```json
{"regression":[{"kind":"duplicate_creators","outcome":"Exactly one renewal per Contract exists after both creation paths run."},{"kind":"shared_parent_lock","outcome":"Concurrent Opportunity saves on the same Account complete without lock errors."},{"kind":"shared_write","outcome":"A save that runs both writers ends with the agreed Opportunity Type."}]}
```

The card supplies these interactions from held evidence. A creation edge or `created_objects` names the record type but does not establish common-parent identity and overlapping conditions, so duplicate creators require card judgement. A fire-chain finding alone creates no story. The five fire-chain groups, standalone validation checks, and changes' boundary cases stay in their existing report or change-story locations. `fire_chain.py targets` can run directly against each option's `elements` before any pick. Card 02 covers every write and creation target, deduplicates identical full targets across options, and shows each shared result on every applicable option. `reads.fire_chain[]` records target, model identifier, sync timestamp, status, result folder and digest path. Card 03 reuses that evidence on its first entry for an identical target on the same model sync; other targets and later entries run normally. Its insert targets cover automations triggered by the created record; the order screen compares writes on the triggering record and does not establish recursive self-trigger behaviour.

The optional `assumptions` input is a list of unanswered option questions as `{question, assumption, elements}`. `elements` lists affected element identifiers, labels or API names. Each assumption attaches to matching change stories and to defect or review stories reached through those changed inputs. An empty `elements` list applies to all change stories. For example, `{"question":"What is multi-year?","assumption":"Multi-year means more than 12 months.","elements":["Type"]}`. The plan stores the assumption text per entry; the finisher adds `Assumes: <assumption>` lines to each affected story description. Both templates' `_option_round_shape.open_questions` records `{question, assumption, answer, elements}`; the card passes unanswered questions from the latest option round only. An absent round supplies an empty list. Empty `assumptions` and `regression` preserve the ordinary plan apart from grouping.

Substantive answers with `kind:"requirement"` enter the plan; the finisher requires them verbatim somewhere in the stories. A bare confirmation contributes no requirement. For `finish_backlog.py`, set `requirement` to `change_request.sentence`. The finisher fills `Request, verbatim:` on change stories, removes that marker from dependent stories, and preserves `Answer, verbatim:`. A missing `problem_statement` comes from the first description line. Markdown preserves description line order and prints a matching first-line problem statement once. Change, defect and review drafts require 3 to 6 criteria and all fixed criteria. A regression draft requires exactly its interaction criteria, including when there is only one or more than six. A plan entry's nonempty flag takes precedence over draft flags. Output stories retain `kind`, `sequence`, `member_count`, `members_file`, `input_ids` and `sources`. The finisher writes `drafted:true`, `flags`, stories and draft status to the backlog record, and puts every blocking flag before the first story in Markdown. Each blocking finding's text is retained even when it matches no individual element. A complete run always drafts.

`delta_keys.py` is the shared delta vocabulary for the dependent digest and backlog plan. Value additions use `values_added`. Value removals use `values_removed`, `values_deleted`, `value_deleted`, or `deleted_values`. Deactivations use `values_deactivated`, `value_deactivated`, or `deactivated`. Renames use `values_renamed`, `api_names_renamed`, `label`, `new_label`, `label_rename`, `api_name`, `new_api_name`, or `api_name_rename`. Report, dashboard and list-view filter stories use removals, deactivations and renames, plus value additions accompanied by another changed writer. `field_name`, `written_fields` and `writes_added_value` share qualified field matching between dependent classification and plan sequencing. A structured write's explicit `parentObject`, `parent_object` or `object` takes precedence over the automation's trigger object; the trigger object qualifies writes that have no explicit parent. Record-type value stories use additions and removals. The migration rule uses `type`, `data_type`, `length`, `values_removed`, `field_required`, and `restricted`. A named automation update records a changed proposed entry condition as `entry_condition_change` in its delta for order-of-execution screening.

`finish_backlog.py` writes an incomplete backlog only when evidence is missing: `drafted:false`, `status:"not drafted"`, the full customer-facing `reason` and an empty story list. Card 04 skips planning for an incomplete run and delivers its report with those files. Blocking findings use the complete draft path with flags.
