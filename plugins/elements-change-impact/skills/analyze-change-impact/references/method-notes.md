# Method notes

The assessment uses the chosen model's last completed sync, read from `get_dependencies` sync recency; it states that sync date. A set `metadataGraphSyncedAt` supplies a complete graph even when the latest `metadataSyncStatus` is `"failed"`; the report shows that date and says "The latest sync failed; this analysis uses the last complete sync." Only a null graph timestamp is `model_not_synced`. A completed zero-row incoming read means nothing references the target; an outgoing read describes what the target uses. Mixed reports give each element's incoming and outgoing counts separately and mark an unassessed direction "not assessed". A read failure is marked with its cause. The named-target table has no last-changed dates. When an automation last-run date matters, read `lastExecuted` from `get_metadata_component` full detail. A mixed automation and schema request follows its primary action; a supporting field can appear as an option element. Named inactive automations can be targets, though the active candidate list does not offer reactivation by default. An unnamed delete redirects to the unused Apex or package uninstall playbook.

The dependency assessment reads direct edges and one additional dependents set for deletion candidates. A field or value delete, deactivation or rename checks reports and list views that filter, bucket or cross-filter on it. Recent reports are named; older reports and reports without a last-used date are counted and listed in a members file. Only active automations count as current readers or writers. For existing-job shortlisting, a null active fact remains eligible unless lifecycle or held definition facts say inactive or deleted. Requested job fields and created objects come from the runner's judgement of the request; existing automation coverage requires outgoing write evidence. Record creation uses structured operation data or an exact operation-only relationship label. Definition gaps produce UNKNOWN units, and an order-of-execution peer without phase or field facts has insufficient evidence. Entry-condition comparisons use current definitions for the baseline and the confirmed proposed conditions for every changed peer. The runner records overlap judgements and evidence in `condition_comparison`; the order screen combines those judgements with current field conflicts to identify pre-existing blocking rows.

Managed code can hide a body. For Apex value literals, `run_code_search` supplements definitions where needed. Dependent-picklist mappings and Path require a manual check. Fire-chain results can be partial even when a traversal finishes, including when references cannot resolve. Each target gets its own call; many written fields can mean many calls. An absent row in a partial result does not prove absence. A new field has no save-driven check until it exists. The report does not display an estimated record volume. A draft story can be thin in a template field; the picked option's element actions control story coverage. Merge and split options have not been demonstrated by a live run.
