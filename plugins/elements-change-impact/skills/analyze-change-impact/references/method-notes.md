# Method notes

The assessment uses the chosen model's last completed sync, read from `get_dependencies` sync recency; it states that sync date. A set `metadataGraphSyncedAt` supplies a complete graph when the latest `metadataSyncStatus` is `"failed"` or `"in_progress"`; the report identifies the latest status and says that analysis uses the last complete sync. Only a null graph timestamp is `model_not_synced`. A completed zero-row incoming read means nothing references the target; an outgoing read describes what the target uses. Mixed reports give each element's incoming and outgoing counts separately and mark an unassessed direction "not assessed". A read failure is marked with its cause. The named-target table has no last-changed dates. When an automation last-run date matters, read `lastExecuted` from `get_metadata_component` full detail. A mixed automation and schema request follows its primary action; a supporting field can appear as an option element. Named inactive automations can be targets, though the active candidate list does not offer reactivation by default. An unnamed delete redirects to the unused Apex or package uninstall playbook.

The dependency assessment reads direct edges, one additional dependents set for deletion candidates, and one incoming hop through formula fields that carry a changed field's value forward. Those formula readers are judged as readers of the changed field. A field or value delete, deactivation or rename checks reports and list views that filter, bucket or cross-filter on it. Recent reports are named; older reports and reports without a last-used date are counted and listed in a members file. Only active automations count as current readers or writers. For existing-job shortlisting, a null active fact remains eligible unless lifecycle or held definition facts say inactive or deleted. Requested job fields and created objects come from the runner's judgement of the request; existing automation coverage requires outgoing write evidence. Work performed inside a managed package is invisible to the existing-automation check; an Extend option can come from source reading outside that check. Record creation uses structured operation data or an exact operation-only relationship label. Definition gaps produce UNKNOWN units, and an order-of-execution peer without phase or field facts has insufficient evidence. Entry-condition comparisons use current definitions for the baseline and the confirmed proposed conditions for every changed peer. The runner records overlap judgements and evidence in `condition_comparison`; the order screen combines those judgements with current field conflicts to identify pre-existing blocking rows. The order-of-execution screen does not establish whether a new automation re-triggers itself on a record it creates. Salesforce does not guarantee the order of two Process Builders on the same object.

Managed code can hide a body. For Apex value literals, `run_code_search` supplements definitions where needed. Picklists backed by a standard value set expose active values only, so the model cannot show inactive values. Dependent-picklist mappings and Path require a manual check. Fire-chain results can be partial even when a traversal finishes, including when references cannot resolve. Each distinct option target gets one call, with results shared across options. The first card 03 entry reuses an identical target's card 02 result on the same model sync. Other targets and later entries receive their own calls. An absent row in a partial result does not prove absence. A new field has no save-driven check until it exists. The report does not display an estimated record volume. A draft story can be thin in a template field; the picked option's element actions control story coverage. Merge and split options have not been demonstrated by a live run.
