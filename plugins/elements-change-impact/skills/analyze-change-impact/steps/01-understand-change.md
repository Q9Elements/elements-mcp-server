# 01 Understand the change

State: `change-requested`

## Purpose

Confirm the requested change against one synced Salesforce model.

## Procedure

1. If the automation-summary prerequisite is pending, retry re-enters card 01: repeat the prerequisite read in step 5, clear the prerequisite block on success, and continue confirmation. While it remains unsatisfied, apply TR-01P; a corrected request returns to target resolution on this card. After delivery, a reply that repeats the recorded pick or confirmation without changing it restores `delivered` and points to the existing deliverables. A reply that changes the request follows the correction route; retry follows TR-03; an option overturn or other added requirement with an option round follows TR-04; an added requirement on a named update or delete follows TR-05 when it only adds build detail (such as a subject line, due date or label); if that requirement adds an element that must change or changes a target, entry condition, field or value, follow the correction route below. For a new request or correction, rebuild `change_request`, preserve the runner's sentence verbatim in `change_request.sentence`, expand grouped names into individual targets, and record replies in `change_request.answers[]` as `{text,kind}`: `requirement` for build criteria, `routing` for corrections or retry, `overturn` for an option reversal. A correction returns to confirmation.
2. Call `get_space_context`, read every `authorized` page, and choose the named or only suitable space. Call `list_reference_models({teamId})` and identify candidate models. For each candidate, resolve its object node id, then make one counts-only `get_dependencies({nodeId:<target object id>,lookingFor:"where_used",mode:"manifest",includePopulation:true})` call. A set `syncRecency.metadataGraphSyncedAt` identifies a complete graph: record it as `change_request.model.last_sync` and continue on the last complete graph even when `metadataSyncStatus` is `"failed"` or `"in_progress"`. Record `latest_sync_failed` on `change_request.model` as true when that status is `"failed"`, otherwise false. Record `latest_sync_in_progress` as true when the status is `"in_progress"`, otherwise false. Record the selected model's `refModelId` and name. Only `metadataGraphSyncedAt` null is `model_not_synced`; if every candidate has a null timestamp, set `blocked.reason=model_not_synced`. If several complete graphs remain and none is named, ask which one in the confirmation message.
3. Classify `kind` as automation or schema and `action` as `decide`, `update` or `delete`. Outcome requests, including multi-element consolidations and requests to create a named element, are `decide`; named changes to existing elements are `update`; named removals are `delete`. Put metadata terms such as Flow or picklist in `intent.mechanism_hint`, not the object slot. Preserve qualifier, write targets, events, effects and capabilities in `intent`. For an ambiguous required type, assume field-level required and say so.
4. Pass written target names, implied types and primary object to `../../scripts/resolve_names.py` with `mode=forms`. Add provisional automation `entry_fields` and `written_fields` forms as Field queries when no held field file exists. Group forms by implied synced type; call `search_metadata` once per implied type as `search_metadata({refModelId,teamId,queries:[<written, normalized and substring forms>],sfType:<implied type>,limit:200,delivery:"file"})`, with `sfType` set for each typed group. Forms of unknown type go in one untyped call with `sfType` omitted, `limit:200` and `delivery:"file"`. Page each group with `skip` while `hasMore` is true, only until every form has an exact-name hit or its results are exhausted. Download each returned file and verify its checksum. Pass the downloaded paths as `hits` to `../../scripts/resolve_names.py`; each file holds a search result object with `nodes`, or rows. For inline results, combine their `nodes` lists as `hits`. Rank the combined hits locally by implied type and parent object. Record zero matches and same-type ties for confirmation; put other unresolved names in `change_request.unresolved[]` and continue. If the runner confirms a target that every synced read still misses, explain that the selected model and sync date do not contain it, and ask them to retry after a sync that includes the target.

5. For resolved targets, call `get_metadata_component({refModelId,teamId,nodeIds:[...],detail:"full",delivery:"file"})` in batches of at most 50. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then pass it to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" get_metadata_component <reply.json> --work <work dir>` to create `nodes.ndjson`. For a named automation, call `get_dependencies({refModelId,teamId,nodeId:<automation id>,lookingFor:"using"})` for trigger object and event edges. Poll each set read with identical arguments while `running`; on `complete`, save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then pass the parts reply to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" <tool> <reply.json> [...] --work <work dir>`. If a part link is stale or its Secure Hash Algorithm (SHA-256) checksum mismatches, make one identical re-call and normalize it. Record each result folder, `status` and manifest totals under `reads`; pass held node bundles as `target_facts` with the named targets to `../../scripts/candidate_digest.py` and read its compact lines. After choosing the space and model, check the automation-summary prerequisite for the target object: call `get_dependencies({refModelId,teamId,nodeId:<target object id>,lookingFor:"where_used"})` once, normalize its reply, and choose one automation on that object. If there is one, call `explain_metadata_components({refModelId,teamId,aspect:"summary",nodeIds:[<automation id>]})`. A target with no automations passes. A refusal or an item with `status:"failed"` and error code `missing_automation_summary`, stops at this card. Record the matching blocked cause and give one instruction: wait for the automation summaries to finish, then say retry. For `running`, poll with identical arguments after `retryAfterSeconds`; clear the prerequisite block when the summary completes. A retry repeats this check on card 01 before confirmation or any later card.
6. For a named automation update, record provisional `delta` with `trigger_object`, `events`, `phase`, `entry_fields` and `written_fields`. Resolve field application programming interface (API) names with `../../scripts/resolve_names.py` using a held field file or the same search hits; record misses in `unresolved[]`. If its entry condition changes, record `entry_condition_change` with the proposed condition. For `update` or `delete`, pass `change_request.targets[]` to `../../scripts/build_change_set.py` and persist its asserted `change_set.elements[]`.
7. For a new request or correction, send one confirmation with the space, model and sync date, action, each target's found status and facts (active, trigger context or data type), and unresolved names. For a named update or delete, offer at most one good alternative in one line within this confirmation: it meets the request's stated intent with materially less change, on strong evidence. Name the alternative and its evidence, including population when relevant. The runner's named change stays the default and is always listed; show an alternative only when it meets this bar. Taking it follows the existing correction route and confirmation. Include any question about several synced models, ambiguous primary object for `decide`, zero matches or same-type ties. Ask the runner to confirm or correct. For an unnamed delete, redirect to the unused Apex or package uninstall playbook.

## Outcomes, in precedence order

- **TR-01P — The automation-summary prerequisite fails or remains unsatisfied.** Record the matching cause and class from `data/blocked-causes.csv`, with `blocked.entered_from="change-requested"` and `blocked.entered_step="steps/01-understand-change.md"`. Write `{"current_state":"change-requested","current_step":"steps/01-understand-change.md"}` together. Give one instruction: wait for the automation summaries to finish, then say retry. Stop here without writing a report or backlog. Next card: `steps/01-understand-change.md` on retry.
- **TR-01 — A required lookup or facts read other than the automation-summary prerequisite fails.** Set `blocked.reason` and `blocked.class` from `data/blocked-causes.csv`, `blocked.entered_from="change-requested"`, and `blocked.entered_step="steps/01-understand-change.md"`. Preserve `blocked.retried=true` after a card 05 retry; otherwise set it false. Write `{"current_state":"blocked","current_step":"steps/05-recover.md"}` together. Next card: `steps/05-recover.md`.
- **TR-02 — A new or corrected understanding awaits confirmation or an applicable ambiguity remains.** Write `{"current_state":"change-requested","current_step":"steps/01-understand-change.md"}` together. Next card: `steps/01-understand-change.md` when the runner replies.
- **TR-03 — A later reply asks to retry an incomplete run.** Write `{"current_state":"<incomplete.entered_from>","current_step":"<dispatch card for incomplete.entered_from>","incomplete":null,"blocked":{"reason":null,"class":null,"entered_from":null,"entered_step":null,"retried":false}}` in one edit. Next card: the dispatch card for `incomplete.entered_from`.
- **TR-04 — A later reply overturns the pick or adds a requirement to a run with an option round.** Put the overturn reason on the latest round when applicable and record the reply's kind. Write `{"current_state":"approach-open","current_step":"steps/02-choose-approach.md"}` together. Next card: `steps/02-choose-approach.md`.
- **TR-05 — A later reply adds only build detail to an update or delete run without adding or changing a target, entry condition, field or value.** Record `{text,kind:"requirement"}`. Write `{"current_state":"impact-traced","current_step":"steps/04-deliver.md"}` together. Next card: `steps/04-deliver.md`.
- **TR-05D — After delivery, the reply repeats the recorded pick or confirmation without changing it.** Write `{"current_state":"delivered","current_step":null}` together. Point to the existing deliverables in `delivery`. Next card: terminal dispatch; stop.
- **TR-06 — The runner confirms a `decide` request.** Write `{"current_state":"approach-open","current_step":"steps/02-choose-approach.md"}` together. Next card: `steps/02-choose-approach.md`.
- **TR-07 — The runner confirms an `update` request or schema `delete` request, and its change set passes the assertion.** Write `{"current_state":"change-set-fixed","current_step":"steps/03-trace-impact.md"}` together. Next card: `steps/03-trace-impact.md`. A confirmed automation `delete` request instead writes `{"current_state":"approach-open","current_step":"steps/02-choose-approach.md"}` and enters card 02 for the existing-automation check before tracing.
- **TR-08 — Otherwise.** Give the redirect or restate the unresolved understanding. Write `{"current_state":"change-requested","current_step":"steps/01-understand-change.md"}` together. Next card: `steps/01-understand-change.md`. Record the default call in `decisions_log` and tell the runner.

## Failure

On a false precondition, recheck the selected space, sync status, names and read pointer. Add the issue and cause to `open_items`; keep this state until evaluation is clean or TR-01 applies. Retry a transient failed read once; a permanent cause in `data/blocked-causes.csv` does not.
