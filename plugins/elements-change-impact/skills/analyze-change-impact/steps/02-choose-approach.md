# 02 Choose the approach

State: `approach-open`

A pending delete-loss question uses `delete-loss-open` and resumes this card.

## Purpose

Present supported create, extend and reuse options, then fix the selected element actions.

## Procedure

1. On re-entry with `current_state:"delete-loss-open"`, use the saved shortlist, summaries, judgements and check output and skip step 2. If the runner has not answered `delete_anyway` or `move`, apply TR-09W and stop. Otherwise record the choice and reply verbatim in `existing_automation.delete_answer` as `{"choice":"delete_anyway"|"move","verbatim":"<reply>"}`, without repeating reads or asking a new question. For `move`, add every uncovered job in `delete.ask`, using `lost_part.job` and `lost_part.reason` for a partial, to the requirement for this card's normal option pick. For `direction:"delete"`, when `delete.ask` is empty or the recorded answer has `choice:"delete_anyway"`, retain card 01's asserted change set, skip steps 3 to 7 and apply TR-10. For `move`, continue with steps 3 to 7 using the uncovered jobs as the requirement. If a pick is pending, interpret the reply here. A pick names the displayed label; rejecting all options requires a reason. Do not route either reply through card 01.
2. Read candidates for the primary object using application programming interface (API) names. For schema, call `list_metadata_by_criteria({refModelId,teamId,metadataList:["Field","Custom Value"],filters:[{"column":"parent_object","operator":"eq","value":"<object API name>"}],columns:["name","api_name","type","subtype","description","active","parent_object","percent_filled"]})`; omit `limit` and `skip`. Join Custom Value rows to their Field using `parentPath=identity`. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper, then pass it to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" list_metadata_by_criteria <reply.json> [...] --work <work dir>`. For automation, reuse held incoming object folders and call `get_dependencies({refModelId,teamId,nodeIds:[<remaining resolved target object ids>],lookingFor:"where_used"})` in batches of at most 1,000 for the other target objects. Include every named target, active or not. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper, then normalize it as in the skill contract. Run `../../scripts/candidate_digest.py` with the result folder, named targets, kind and primary `object`; read its entire output. Save the held change set, including an empty `{"elements":[]}` for a decide request, as `change_set.json`. Before building options on a new entry, run `../../scripts/existing_jobs.py shortlist --change-set <change_set.json> --objects <resolved target object API names> --dependents <normalized folder> [...] --out <shortlist.json>`, using the target objects resolved by card 01 and the card 01 and card 02 normalized dependency folders. Include `--definitions <held normalized definition folders>` when definitions are held so explicit inactive or deleted definitions exclude candidates. Call `get_dependencies({refModelId,teamId,nodeIds:[<shortlisted candidate, deleted automation and active peer ids>],lookingFor:"using"})` in batches of at most 1,000 before reading summaries. Include every shortlisted candidate, including Apex classes with a null active fact, every deleted automation so job writes are held, and the active peer inventory for order-of-execution screening. Save each reply as `{"_call":{"nodeIds":[...]},"response":<reply>}`, then run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" get_dependencies <reply.json> [...] --work <work dir>`. Store each normalized candidate using folder in `reads`. For each `summary_id`, read `explain_metadata_components({refModelId,teamId,aspect:"summary",nodeIds:[...]})` in batches of at most 25; poll `running` with identical arguments after `retryAfterSeconds` and save every completed inline reply. For Workflow Rule candidates, use definition text from the definitions folder card 02 already holds, or read it with `get_metadata_source`. Judge whether each new request is already done, partially done or not done; for a delete, split the deleted automation's summary into its jobs and judge each job against each shortlisted candidate. Write `judgements.json` in the shared contract shape: `items[]` with `direction`, `job`, `job_fields`, `creates_object`, `candidate`, `verdict` and `reason`. For a new request, state `job`, `job_fields` and `creates_object` from the request in `judgements.json`; for a delete, use one item per deleted job and candidate, and the deleted automation's write edges for `job_fields`. Then run `../../scripts/existing_jobs.py check --shortlist <shortlist.json> --summaries <saved summary reply> [...] --judgements <judgements.json> --dependents <held dependency folders> <candidate using folders> --change-set <change_set.json> --out <existing-jobs.json>`. Keep summaries and judgements as report evidence, not chat. A fit becomes the first option of the existing pick, shown as `Use what you already have: <name> (<type>) <summary>. It writes <field>.`; a partial becomes an `Extend <name>` option. For a delete, if `delete.ask` is nonempty and `existing_automation.delete_answer` is null, ask once: `Deleting <name> removes: <job>. Nothing else in the org does this. Delete anyway, or move it first?` Include every entry in `delete.ask` in that one question. The list combines `lost` and `partly_covered`; for a partial, name the uncovered work with `lost_part.job` and `lost_part.reason`. Write `{"current_state":"delete-loss-open","current_step":"steps/02-choose-approach.md"}` while awaiting the answer. If `delete.ask` is empty, continue without a question. A `move` reply sends every uncovered job from `delete.ask`, including each partial's lost part, into the normal option pick as requirements; `delete_anyway` continues with the known loss. For `direction:"delete"`, when `delete.ask` is empty or the recorded answer has `choice:"delete_anyway"`, retain card 01's asserted change set, skip steps 3 to 7 and apply TR-10. After writing the pending question, apply TR-09W and stop. For a recorded `move`, continue with steps 3 to 7 using every uncovered job as the requirement. This check adds no other stop.
3. If `targets[]` is nonempty, call `get_metadata_source({refModelId,teamId,nodeIds:[<target ids>]})` in batches of at most 5,000. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper, then pass it to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" get_metadata_source <reply.json> [...] --work <work dir>`, then pass its `index.csv` to `../../scripts/definitions_digest.py` with target names. Save the result folder in `reads`; card 03 reuses it for those targets. Reuse the candidate using folders from step 2 for peer edges. Run `../../scripts/ooe_screen.py` with each proposed automation option, full inventory, peer edge result folder and `data/ooe-rules.csv`. For update or extend, set `change.existing_written_fields` from the host automation's outgoing write edges. Treat `RecordBeforeAndAfterSave` as both phases and take Flow kind from facts. Exclude peers deleted by the option and peers with inactive or Obsolete definitions.
4. Build one create option and every real reuse or extend fit from the candidate file. Each option records `label`, `mode`, `summary`, `elements[] {element,action,delta}`, evidence and order-of-execution status. Resolve option `entry_fields` and `written_fields` with `../../scripts/resolve_names.py` using a held field file or the same search hits; retain unresolved names. For each new automation, record every object API name in `delta.created_objects`, or `[]` if it creates none. If a delete moves logic to a created or updated automation, record that automation's API name in the delete's `delta.replacement`. Existing elements must come from the candidate file or the shortlisted automations; preserve their identifiers and types. Create options name the proposed new element. Give every named target an action, using `keep` with an empty delta when unchanged. A value, restriction, placement or required change is `update`.
5. Before asking for a pick, call `get_dependencies({refModelId,teamId,nodeIds:[<all existing option elements>],lookingFor:"where_used"})` in batches of 1,000. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper, then normalize it as in the skill contract. Pass the options, candidate result folder, dependents result folder and target facts to `../../scripts/option_evidence.py`. If a pre-pick read fails after one transient retry, mark its evidence `<evidence>: not available (<cause>)`; for `<cause>`, use the tool's own message when present; otherwise use the customer text of the matching `data/blocked-causes.csv` row. Keep the pick available. If the recommendation depends on that gap, say "say retry to fill it in before you pick".
6. Present the recommended option first with its reason, then all others. A fit for an existing automation that already does this leads the options and chat; show its summary and written field in the option. For each option, show mode, touched names and types, rationale, pros and cons, peer order status including any blocking row, dependent totals by type, migration and population consequences, and org-pattern fit. Put open questions under "answer any you know". Show labels and names, not option or node identifiers. Ask the runner to pick one option in this single stop.
7. On a pick, record `picked`, `why` and `set_aside` reasons in the latest `option_rounds[]`. Pass its elements and `change_request.targets[]` to `../../scripts/build_change_set.py`. Require an action for every named target; repair omissions and rerun the assertion. Store the asserted `change_set.elements[]`.

## Outcomes, in precedence order

- **TR-09 — The candidate set read fails.** Set `blocked.reason` and `blocked.class` from `data/blocked-causes.csv`, `blocked.entered_from="approach-open"`, and `blocked.entered_step="steps/02-choose-approach.md"`. Preserve `blocked.retried=true` after a card 05 retry; otherwise set it false. Write `{"current_state":"blocked","current_step":"steps/05-recover.md"}` together. Next card: `steps/05-recover.md`.
- **TR-09W — The delete-loss question is pending and the runner has not answered `delete_anyway` or `move`.** Write `{"current_state":"delete-loss-open","current_step":"steps/02-choose-approach.md"}` together, preserve the saved question and evidence, and stop for the answer. Next card: `steps/02-choose-approach.md` when the runner replies.
- **TR-10 — The runner picks an option and change-set coverage passes, or the confirmed change has `direction:"delete"` and either `delete.ask` is empty or the runner chooses `delete_anyway`.** Write `{"current_state":"change-set-fixed","current_step":"steps/03-trace-impact.md"}` together. Next card: `steps/03-trace-impact.md`.
- **TR-11 — Otherwise.** If every option was rejected with a reason, append `rejected_all_reason` to the latest round and `change_request`, rebuild from the candidate file and announce the new options. If the pick is pending, keep the displayed options. Write `{"current_state":"approach-open","current_step":"steps/02-choose-approach.md"}` together. Next card: `steps/02-choose-approach.md`. Record the default call in `decisions_log` and tell the runner.

## Failure

If an option refers to a missing candidate, a named target has no action, or a bundle cannot be checked, add the defect to `open_items` and recheck the candidate file or pointer. Keep this state until the option and assertion are valid or TR-09 applies. Retry a transient read once; keep an evidence gap visible after two failures.
