# 03 Trace impact

State: `change-set-fixed`

## Purpose

Trace the fixed change set to dependents, required work, order conflicts and save-driven effects.

## Procedure

1. On every entry, rerun the card from `change_set.elements[]`. If every action is `keep`, record no impact reads and one "Adopt as is" plan entry. Otherwise make required `get_dependencies` reads over changed existing elements: schema updates and every delete use incoming `lookingFor:"where_used"`; automation updates use incoming `lookingFor:"where_used"` and outgoing `lookingFor:"using"`. Include the field's object for a field-level required delta and the created automation's resolved `entry_fields` for its trigger-field check. Batch node ids at 1,000; pass one `sfType` per call only when a type filter is needed. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then normalize it as in the skill contract and record totals from the synthesized `manifest.json`, including zero rows. A failed required dependents read follows TR-12.
2. For each existing changed picklist value, read its Field and Custom Value rows with `list_metadata_by_criteria({refModelId,teamId,metadataList:["Field","Custom Value"],filters:[{"column":"parent_object","operator":"eq","value":"<object API name>"}],columns:["name","api_name","type","subtype","description","active","parent_object","percent_filled"]})`; omit `limit` and `skip`. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then pass it to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/normalize_reads.py" list_metadata_by_criteria <reply.json> [...] --work <work dir>`. Join Custom Value rows to their Field with `parentPath=identity` and match name or application programming interface (API) name to resolve node id and active state. A newly proposed value has no synced value node; check its proposed literal in definitions without treating that absence as a failed read. For a global value set (GVS), call `get_dependencies({refModelId,teamId,nodeId:<set id>,lookingFor:"where_used"})`, resolve and scan every field-level value copy. Call `get_dependencies({refModelId,teamId,nodeIds:[<affected value ids>],lookingFor:"where_used"})` in batches. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then normalize it as in the skill contract. When a dependent is a formula field that carries the changed field's value forward, read its definition, then call `get_dependencies({refModelId,teamId,nodeIds:[<value-carrying formula field ids>],lookingFor:"where_used"})`. Normalize those replies and read their dependent definitions with step 3. Follow one additional hop through these formulas and judge their incoming dependents as if they depended on the changed field. For example, a quote formula carrying Opportunity Type can expose Apex readers comparing it to a specific Type literal. Save each changed field's carrier identifiers as `formula_input_ids` for step 4. Read `lastUsed` from the converter when `related.lastRun` is present. Dependency rows can have no last-run value; when a card relies on an automation's last run, read its `get_metadata_component({refModelId,teamId,nodeId:<automation id>,detail:"full"})` detail and use `lastExecuted`. Use report `lastUsed` for the 90-day split. A missing existing value node is UNKNOWN, never zero.
3. Call `get_metadata_source({refModelId,teamId,nodeIds:[<changed automation and judgement-row ids>]})` in batches of 5,000, omitting named targets whose definition result folder card 02 holds. Save each reply with its call's `nodeIds` or `nodeId` in the Session contract wrapper or minimal manifest, then normalize it and pass the result folder, target API names and old and new value literals to `../../scripts/definitions_digest.py`. For affected picklist values, check quoted API-name literals in available Apex bodies and call `run_code_search({refModelId,teamId,query:"'<value API name>'"})` for possible source hits outside those bodies; poll `running` with identical arguments and download parts. Preserve refusal and source-unavailable messages in the evidence gap.
4. Run `../../scripts/dependents_digest.py` once per changed element, passing that element's node id as `input_node_id`, its own mode, the dependents bundle, definition digest, the full `change_set`, changed values and `data/relation-kinds.csv`. The script keeps only rows whose `inputNodeId` is that element or its parent field for a Custom Value; the full change set remains available for the added-value writer check. Pass that field's `formula_input_ids` and the formula dependent folders on the same digest call; the script retains the changed field as `inputNodeId` and records the carrier as `viaFormulaNodeId`. The digest classifies every relation before combining a component, retaining its strongest effect and all source relations. Merge each element's resulting units once; retain `sources` when adding a cited judgement so the backlog planner keeps every changed input and formula path on one component story. Use active state when describing current readers or writers; an inactive definition remains a reference to assess. For Flow, Process Builder Workflow, Apex Class, Apex Trigger, Workflow Rule, validation rule and formula-field judgement rows on value or type updates, renames, deactivations, value deletes and element deletes, judge the snippet here. On update choose UPDATE or NOT_IMPACTED with a cited reason; on delete remove the reference by UPDATE, or choose DELETE_CANDIDATE only when the snippet shows sole purpose. No definition means UNKNOWN. Other rows follow the table. Do not make a backlog unit from a no-story row.
5. For field or value delete, deactivation or label/API-name rename, include every report or list view with a filter, bucket or cross-filter on it in its grouped review story, regardless of operator. Say its records change and ask the owner to confirm the filter. List affected list views by name. When a value add is written onto records by another change-set element, include Reports and Dashboards together in one grouped review story and List Views in another. Add one manual-check line for dependent-picklist mappings and Path. If a field becomes required at field level, check record-creating automations on its object and give an UPDATE unit to each that does not set the field.
6. For `DELETE_CANDIDATE` ids, call `get_dependencies({refModelId,teamId,nodeIds:[...],lookingFor:"where_used"})`, normalize the parts, and pass the result folder, dispositions and change set to `../../scripts/delete_order.py`. For a named automation update whose delta adds written fields, changes phase, or has `entry_condition_change`, run `../../scripts/ooe_screen.py` on its full active peer inventory and read/write edges with `data/ooe-rules.csv`. Read that inventory with `get_dependencies({refModelId,teamId,nodeId:<triggering object id>,lookingFor:"where_used"})`, then read its active peers with `get_dependencies({refModelId,teamId,nodeIds:[<active peer ids>],lookingFor:"using"})`, normalizing each parts reply. For each blocking row on an entry-condition change, compare the current conditions from held definitions, then compare the host's proposed condition with the peer's proposed condition from `change_set.elements[]` when that peer is changed in the confirmed set; use the held current condition for an unchanged peer. Record whether each pair can match the same record in the peer input's `condition_comparison` as `{current_overlap: true|false|null, proposed_overlap: true|false|null, analyst_note: <comparison and evidence>}` and rerun `ooe_screen.py`. Use null for an unresolved comparison. The script combines `current_overlap` and `proposed_overlap` with its baseline field screen to set `pre_existing`; retain an unchanged overlap as pre-existing. Write any downgrade reason in the row's `analyst_note`. Leave `reason` exactly as `ooe_screen.py` wrote it. If they cannot match, downgrade the row to manageable and explain why in `analyst_note`; if unresolved, keep it blocking and explain why there. If none of the three triggers applies, record "no written-field, timing or entry-condition change".
7. Pass the change set and current active write edges, as one path or a list of paths, to `../../scripts/fire_chain.py targets`. On the first entry, reuse card 02's result in `reads.fire_chain[]` for an identical target on the same model sync: match model identifier, sync timestamp and the full target (`object`, `operation`, sorted `writtenFields`, `estimatedVolume`). Reuse its status, result folder and digest without another call. For every other target and on later entries, pass it to `run_data_load_impact({refModelId,teamId,targets:[<target>]})`. Poll `running` with identical arguments, fetch `complete`, and download the zip with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/fetch_bundle.py" --url <bundleUrl> --sha256 <bundleSha256> --work <work dir> --job-id <jobId>` before passing its folder with status and `change_set` to `../../scripts/fire_chain.py digest`. Partial results come from `coverage.json`; preserve each stop reason, including tool wording such as "no flows, triggers or rules with write access were found". On `fire_chain_analyses_at_capacity`, wait for server capacity and retry the same call; this is server busy, not a blocked cause. A `failed` status reads `error.code`. A create field says "the field does not exist yet"; a field or automation delete without save-driven work has no call. Record failed nonrequired reads as `not available (<cause>)`; for `<cause>`, use the tool's own message when present; otherwise use the customer text of the matching `data/blocked-causes.csv` row.
8. Save paths, counts, partial flag and concise `analysis.material_findings[]` as `{text, blocking, needs_repick, element}`. Set `blocking:true` only when no story in the backlog resolves it and it makes the change unsafe as planned; name the changed element by node identifier or API name. A finding whose fix is a backlog story is reported with `blocking:false`. For example, existing readers corrected by defect stories remain report findings; an unresolved order conflict created by the change or a blast radius materially larger than the option evidence can be blocking. Set `needs_repick:true` only when the finding may change the runner's approach choice. Record post-pick blocking order conflicts and blast-radius or migration needs missing from option evidence for card 04. A fact about an existing path stays in the report. Identify cross-story interactions for a regression story only when at least one applies: two or more automations can create the same kind of record for the same parent; a fire-chain lock is on a shared parent; or two changed elements, or a changed element and existing automation, write the same field in the same save. Save each interaction in `analysis.regression[]` as `{kind,outcome,elements}`: `kind` is `duplicate_creators`, `shared_parent_lock` or `shared_write`; `outcome` is an end-to-end outcome; `elements` names the changed elements by identifier, label or API name. `created_objects` alone does not prove duplicate creators: confirm a common parent and overlapping conditions from held evidence. Replace the saved list with the interactions found on this entry, using `[]` when none apply. Bundle rows stay in files. The card has no runner stop.

## Outcomes, in precedence order

- **TR-12 — The required dependents read fails.** Set `blocked.reason` and `blocked.class` from `data/blocked-causes.csv`, `blocked.entered_from="change-set-fixed"`, and `blocked.entered_step="steps/03-trace-impact.md"`. Preserve `blocked.retried=true` after a card 05 retry; otherwise set it false. Write `{"current_state":"blocked","current_step":"steps/05-recover.md"}` together. Next card: `steps/05-recover.md`.
- **TR-13 — Every analysis step finished or recorded `not available (reason)`.** Write `{"current_state":"impact-traced","current_step":"steps/04-deliver.md"}` together. Next card: `steps/04-deliver.md`.
- **TR-14 — Otherwise.** Mark the unfinished step `not available (reason)`, write `{"current_state":"impact-traced","current_step":"steps/04-deliver.md"}` together. Next card: `steps/04-deliver.md`. Record the default call in `decisions_log` and tell the runner.

## Failure

If the change-set assertion, node identity or disposition precondition is false, recheck the change set and source bundles and add the cause to `open_items`. Keep this state until evidence is coherent, TR-12 applies or a nonrequired read is marked unavailable. Retry transient reads once; permanent causes receive no automatic retry.
