# 04 Deliver

State: `impact-traced`

## Purpose

Deliver a reviewable impact report and draft backlog, including incomplete results.

## Procedure

1. When `incomplete` is null, always pass `change_set`, dispositions, delete order, material findings, `change_request.answers[]`, `analysis.regression` as `regression`, and unanswered card 02 open questions as `assumptions` to `../../scripts/plan_backlog.py`; it writes `story-plan.json`. Resolve a relative `engagement` path from the process working directory, or pass an absolute path. Pass any story the runner explicitly requests as `requested_stories`, with a summary and verbatim request. Each assumption has `{question,assumption,elements}` and comes from unanswered items in the latest option round's `open_questions` only. An absent option round supplies `[]`. Pass only interactions found in this run; a TR-05 redelivery reuses the saved list when card 03 is skipped. A blocking finding never holds the plan: it leads the report and appears as a flag at the top of both backlog files with its text. A `keep` element has no story unless every element is `keep`, when the plan contains "Adopt as is". The plan contains change, defect, grouped review and regression stories only. Add a defect story for each card-judged dependent with UPDATE, DELETE or DELETE_CANDIDATE. Group script-decided review units by type and relation as specified by the plan. Put facts about existing paths in the report. Add a regression story only for a cross-story interaction passed in `regression`. A delete story starts with deactivation when the deleted target is an active automation or rule; when a replacement Flow is in the change set, require it to be active and produce the same field results on a sample record before deletion. A field or already inactive target has no deactivation step.
2. Write each story's summary, description, acceptance criteria and implementation details. Each change story's acceptance criteria define its tests, including boundary cases of the change's own condition; include no separate test list. Attach `Assumes: <assumption>` to each story that rests on an unanswered card 02 question, using its `elements` and the story's change. Put each `{kind:"requirement"}` answer verbatim on its matching change story, or the story when the target is unclear. Prefix answer lines `Answer, verbatim:` and the original request on its change story `Request, verbatim:`. A grouped review story lists its members and gives the review criteria for that family. A regression story contains one end-to-end criterion per cross-story interaction. Pass the completed plan to `../../scripts/finish_backlog.py`; repair any answer-placement or coverage assertion failure and rerun it. If `incomplete` is set, skip planning and write both backlog files with `drafted:false` and "not drafted" plus the cause's customer text from `data/blocked-causes.csv`.
3. Copy `templates/impact-report.json` to the engagement's `impact-report.json` and fill it from state and held bundles. Use the runner's original sentence verbatim as the headline, followed by space, org and named targets. Copy `change_request.model.last_sync`, `latest_sync_failed` and `latest_sync_in_progress` from state. For each successful dependency read on a changed element, set `impacted_components.read_counts[<node id>].incoming` or `.outgoing` from its normalized rows, retaining zero for a completed empty read; use the saved call's `lookingFor` to identify the direction and manifest inputs to confirm which elements were read. Omit an unassessed direction. Preserve each member's `inputNodeId` and `direction`. The report separates incoming dependents from outgoing connections and says "not assessed" for an unassessed direction. When `latest_sync_failed` is true, say "The latest sync failed; this analysis uses the last complete sync." When `latest_sync_in_progress` is true, say "A newer sync is in progress; this analysis uses the last complete sync." Include options and pick history; map `existing_jobs.py check` output `new.fits` and `new.partials` to `existing_automation.fits` and `existing_automation.partials`, copy its delete arrays to `covered`, `partly_covered` and `lost`, and copy the recorded reply to `delete_answer`; impacted-component dispositions and counts, including UNKNOWN, true zero and delete order; "Not in the backlog: review before build" with fire-chain groups, next hops, trigger-field check, order rows, partial flag and one lock line per relationship; evidence drawers with facts before model text; backlog in plan order with flags and "Draft only: not saved as Elements stories"; limits from `references/method-notes.md`; and corrections to the runner's understanding. When the fire-chain read is unavailable, set `review_before_build.fire_chain_unavailable` to `<cause>`; for `<cause>`, use the tool's own message when present; otherwise use the customer text of the matching `data/blocked-causes.csv` row, or `model_not_synced` while the model syncs. A create-only change set says "not assessed against existing elements: no existing target". An incomplete report marks each missing section and cause.
4. Lead the report and chat with an existing automation that already does this when the purpose and write check confirm a fit, then lead with each blocking finding and any material blast-radius or migration need absent from option evidence. Every blocking finding remains a flag on the backlog. Show a pre-pick evidence gap as `not available, failed twice (cause)` in the affected option. Drawers use held bundle rows; make no new Elements read. Render `impact-report.html` from `impact-report.json` with `../../scripts/render_report.py`. Copy card 03's findings into `material_findings` in the report record and set `blocking` and `element` for findings to resolve before build, and set `needs_repick: true` only for qualifying findings when the run had an option round. Put blocking findings under "Findings to resolve before build" and others under "Findings".
5. Set `delivery` paths, story counts by create, update and delete, and flag notes. Tell the runner the files, counts, deploy order and important flags in a few lines. The backlog is a draft and has not been saved as Elements stories. On an incomplete run say "say retry when <fix>" using `data/blocked-causes.csv`. Complete the delivery outcome and stop.

## Outcomes, in precedence order

- **TR-15 — The report record, report page and both backlog files are written.** Write `{"current_state":"delivered","current_step":null}` together. Next card: terminal dispatch; report the deliverables and stop.
- **TR-16 — Otherwise.** If a plan coverage assertion failed, record the assertion failure as an incomplete cause, deliver the full report and mark the backlog not drafted with that cause. Write `{"current_state":"delivered","current_step":null}` together. Next card: terminal dispatch; report the defect. Record the default call in `decisions_log` and tell the runner.

## Failure

If state lacks a confirmed change request, change set or explained incomplete cause, recheck the preceding card and add the missing item to `open_items`. Keep this state until inputs are coherent. If rendering fails, repair the report record and rerender before presenting it.
